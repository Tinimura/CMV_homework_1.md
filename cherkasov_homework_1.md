## Завдання 1. Дослідження мережі

**Команда:**

```bash
ip a
```

**Фактичний результат:**

```text
micheal@ASUSTUF-MISHA:~$ ip a
1: lo: <LOOPBACK,UP,LOWER_UP> mtu 65536 qdisc noqueue state UNKNOWN group default qlen 1000
    link/loopback 00:00:00:00:00:00 brd 00:00:00:00:00:00
    inet 127.0.0.1/8 scope host lo
       valid_lft forever preferred_lft forever
    inet 10.255.255.254/32 brd 10.255.255.254 scope global lo
       valid_lft forever preferred_lft forever
    inet6 ::1/128 scope host proto kernel_lo
       valid_lft forever preferred_lft forever
2: eth0: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1280 qdisc mq state UP group default qlen 1000
    link/ether 00:15:5d:cf:1e:69 brd ff:ff:ff:ff:ff:ff
    altname enx00155dcf1e69
    inet 172.19.82.23/20 brd 172.19.95.255 scope global eth0
       valid_lft forever preferred_lft forever
    inet6 fe80::215:5dff:fecf:1e69/64 scope link proto kernel_ll
       valid_lft forever preferred_lft forever
```

**Визначені параметри:**

| Параметр | Значення | Пояснення |
|---|---|---|
| Мережевий інтерфейс | `eth0` | Активний мережевий інтерфейс Ubuntu у WSL (`state UP`) |
| Тип підключення | Віртуальний Ethernet | З'єднання між WSL та мережевим стеком Windows; не підтверджує тип фізичного підключення ПК |
| MAC-адреса | `00:15:5d:cf:1e:69` | Канальний рівень OSI (2) |
| Локальна IPv4-адреса | `172.19.82.23` | Мережевий рівень OSI (3), приватна адреса |
| Маска підмережі | `255.255.240.0` (`/20`) | Використовується для визначення меж IPv4-підмережі, мережевий рівень OSI (3) |
| Адреса підмережі | `172.19.80.0/20` | Обчислена з адреси та маски; також підтверджена командою `ip r` |
| Шлюз за замовчуванням (gateway) | `172.19.80.1` | Визначено за результатом `ip r` |
| Broadcast | `172.19.95.255` | Широкомовна адреса підмережі, наведена у `ip a` |
| Hosts | **4094 придатні адреси** | Діапазон `172.19.80.1`–`172.19.95.254`; частину адрес можуть займати шлюз та інші пристрої |

**Пояснення розрахунку:** префікс `/20` означає 20 біт для мережі та 12 біт для адрес вузлів. Загальна кількість IPv4-адрес у цій підмережі: `2^12 = 4096`; зазвичай дві з них зарезервовані під адресу мережі та broadcast, тому `4096 − 2 = 4094` придатні адреси. Це кількість можливих адрес, а не фактично підключених пристроїв.

Інтерфейс `lo` є петльовим інтерфейсом (loopback); його адреса `127.0.0.1/8` використовується для взаємодії програм у межах тієї самої системи й не є основною адресою для виходу в мережу.

**Висновок:** у досліджуваному середовищі Ubuntu працює віртуальний інтерфейс `eth0` з приватною IPv4-адресою `172.19.82.23/20`. MAC-адреса належить до рівня 2 OSI, а IPv4-адреса та адресація підмережі — до рівня 3 OSI.

## Завдання 2. Дослідження маршрутизації

**Команда:**

```bash
ip r
```

**Фактичний результат:**

```text
micheal@ASUSTUF-MISHA:~$ ip r
default via 172.19.80.1 dev eth0 proto kernel
172.19.80.0/20 dev eth0 proto kernel scope link src 172.19.82.23
```

**Аналіз маршрутів:**

1. `default via 172.19.80.1 dev eth0 proto kernel` — маршрут за замовчуванням. Пакети до адрес, для яких немає більш конкретного маршруту, спрямовуються через шлюз `172.19.80.1` за інтерфейсом `eth0`.
2. `172.19.80.0/20 dev eth0 proto kernel scope link src 172.19.82.23` — маршрут до безпосередньо підключеної підмережі `172.19.80.0/20`. Для адрес цієї мережі окремий маршрутизатор не потрібен; як вихідна IPv4-адреса використовується `172.19.82.23`.

**Протокол:** в обох рядках зазначено `proto kernel`. Це позначення походження запису маршруту в таблиці Linux, а не доказ отримання IPv4-адреси через певний протокол. За одним лише `ip r` не можна достовірно визначити, чи була адреса призначена за DHCP, вручну або механізмами WSL. Для підтвердження способу призначення адреси потрібні окремі дані мережевої конфігурації.

**Додаткова перевірка доступності маршруту:**

```bash
ping -c 3 172.19.80.1
ping -c 3 1.1.1.1
getent ahostsv4 api.ipify.org
```

Результати: шлюз `172.19.80.1` відповів на 3 з 3 ICMP-запитів (0% втрат); зовнішня IPv4-адреса `1.1.1.1` також відповіла на 3 з 3 запитів (0% втрат). Ім'я `api.ipify.org` успішно перетворилося на IPv4-адреси `104.26.13.205`, `104.26.12.205` та `172.67.74.152`.

**Висновок:** система має маршрут до локальної підмережі та маршрут за замовчуванням через віртуальний шлюз WSL. ICMP-зв'язність із шлюзом і зовнішнім вузлом підтверджена; це саме по собі не гарантує доступність усіх TCP-сервісів.

## Завдання 3. Знаходження публічної IP-адреси

**Команда за умовою завдання:**

```bash
curl ifconfig.io
```

**Фактичний результат у WSL:**

```text
micheal@ASUSTUF-MISHA:~$ curl ifconfig.io
curl: (28) Failed to connect to ifconfig.io port 80 after 134483 ms: Could not connect to server
```

Була також здійснена спроба отримати публічну IPv4-адресу через HTTPS:

```bash
curl -4 -sS --max-time 10 https://ifconfig.io/ip
curl -4 -sS --max-time 10 https://api.ipify.org
```

Обидва запити завершилися `curl: (28) Connection timed out`. Детальна перевірка `curl -4 -v --connect-timeout 5 --max-time 12 https://api.ipify.org` показала, що доменне ім'я визначалося, але TCP-з'єднання з портом `443` не встановилося. Перевірка `env | grep -i proxy` не виявила змінних середовища проксі.

**Публічну IPv4-адресу було отримано альтернативним способом через Windows, із зовнішнього сервісу визначення IP-адреси:**

```text
85.238.97.100
```

> Ця адреса отримана не як успішний результат `curl ifconfig.io` в Ubuntu; вказані вище помилки залишено у звіті для достовірності практичних спостережень.

**Порівняння:**

| Характеристика | Локальна адреса WSL | Публічна IPv4-адреса |
|---|---|---|
| Значення | `172.19.82.23` | `85.238.97.100` |
| Призначення | Адреса віртуальної приватної мережі WSL | Адреса, яку бачить зовнішній сервіс при зверненні з Windows |
| Доступність безпосередньо з Інтернету | Не маршрутизується в публічному Інтернеті | Належить до публічного IPv4-простору; це не означає, що вхідні з'єднання дозволені |

**Чи однакові ці адреси?** Ні, вони різні.

**Чому вони різні?** Адреса `172.19.82.23` належить до приватного діапазону `172.16.0.0/12`, який не маршрутизується у глобальному Інтернеті. У досліджуваній конфігурації WSL має власну віртуальну підмережу і шлюз. Під час виходу в Інтернет Windows або інший мережевий пристрій може виконувати трансляцію мережевих адрес (NAT), замінюючи внутрішню адресу на адресу, придатну для зовнішнього обміну. Домашній маршрутизатор також часто використовує NAT для кількох пристроїв домашньої мережі. При цьому з наведених команд не можна встановити точну кількість NAT-переходів чи стверджувати, що `85.238.97.100` призначена безпосередньо домашньому маршрутизатору.

**Висновок:** локальна адреса Ubuntu у WSL (`172.19.82.23`) і визначена через Windows зовнішня адреса (`85.238.97.100`) не збігаються. Це пояснюється відокремленням приватної віртуальної адресації від публічної мережі та можливою трансляцією адрес. Команда `curl ifconfig.io` у WSL не дала результату через тайм-аут TCP-з'єднання, тому альтернативний метод отримання публічної адреси зазначено окремо.
